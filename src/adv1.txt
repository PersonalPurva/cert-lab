#D 51|RH134|Advanced LVM: snapshots|Create, use and merge LVM snapshots to capture and roll back a logical volume.
Q What is an LVM snapshot?
+ A point-in-time copy of a logical volume that only stores changed blocks
- A full independent copy of the volume
- A backup stored off the disk
- A read-only clone that never changes
E Snapshots use copy-on-write, so they start tiny and grow as the origin changes.
Q What happens if a snapshot's allocated space fills up completely?
+ The snapshot becomes invalid (dropped) and can no longer be used
- The origin volume is deleted
- The system reboots
- Nothing; it auto-extends forever
E Size the snapshot for the expected amount of change, or enable auto-extend in lvm.conf.
Q Which command reverts an origin volume to its snapshot's state?
+ lvconvert --merge /dev/vg/snap
- lvrevert /dev/vg/snap
- lvrestore /dev/vg/snap
- lvcreate --rollback
E If the origin is in use, the merge happens at the next activation/reboot.
Q In `lvs`, which columns tell you a snapshot's origin and how full it is?
+ Origin and Data%
- Attr and Size only
- Move and Log
- Meta% and Pool
E Watch Data% — at 100% the snapshot is lost.
Q Why take a snapshot before a risky upgrade or edit?
+ You can quickly roll the volume back to the pre-change state if it breaks
- It speeds up the upgrade
- It encrypts the volume
- It is required by systemd
E Snapshots are a fast local "undo" — not a replacement for real backups.
Q A snapshot is best used as a stable source for:
+ Taking a consistent backup while the origin keeps changing
- Permanent long-term storage
- Growing the volume group
- Swap space
E Back up from the frozen snapshot, then remove it.
C Create a 1 GiB snapshot named datasnap of the logical volume /dev/vgdata/lvdata.
A lvcreate -s -n datasnap -L 1G /dev/vgdata/lvdata
A lvcreate --snapshot -n datasnap -L 1G /dev/vgdata/lvdata
E -s makes it a snapshot; the origin is the last argument.
C Show all logical volumes including snapshots, with their origin and usage.
A lvs -a -o +origin,data_percent
A lvs -a
E `lvs -a` reveals hidden internal volumes; add columns to see snapshot detail.
C Merge the snapshot /dev/vgdata/datasnap back into its origin.
A lvconvert --merge /dev/vgdata/datasnap
E After merging, the snapshot is automatically removed.
T Snapshot, break, and roll back (exam-plus)
S On lvdata (mounted at /mnt/data with a file inside), take a snapshot, deliberately corrupt the data, then roll back using the snapshot and prove the file returned.
X echo "good version" > /mnt/data/report.txt
X lvcreate -s -n datasnap -L 1G /dev/vgdata/lvdata
X echo "corrupted" > /mnt/data/report.txt
X umount /mnt/data
X lvconvert --merge /dev/vgdata/datasnap
X mount /dev/vgdata/lvdata /mnt/data
V cat /mnt/data/report.txt      # shows "good version"
T Consistent backup from a snapshot
S Snapshot lvdata, mount the snapshot read-only, back it up with tar, then remove the snapshot.
X lvcreate -s -n bsnap -L 500M /dev/vgdata/lvdata
X mkdir -p /mnt/snap && mount -o ro /dev/vgdata/bsnap /mnt/snap
X tar -czf /root/data-backup.tar.gz -C /mnt/snap .
X umount /mnt/snap && lvremove -y /dev/vgdata/bsnap
V tar -tzf /root/data-backup.tar.gz | head; lvs | grep -c bsnap   # 0 left
T Watch a snapshot fill up
S Create a small (100 MiB) snapshot, then write more than 100 MiB into the origin and observe the snapshot become invalid.
X lvcreate -s -n tiny -L 100M /dev/vgdata/lvdata
X dd if=/dev/zero of=/mnt/data/bigfile bs=1M count=200
X lvs -a -o +data_percent      # tiny shows 100% then goes invalid
X rm /mnt/data/bigfile
V lvs shows the snapshot invalidated (Attr has an 'I'); you understand sizing

#D 52|RH134|Advanced LVM: thin, striped and RAID volumes|Build thin-provisioned, striped and mirrored/RAID logical volumes.
Q What is thin provisioning in LVM?
+ Logical volumes can present more space than is physically allocated, using a shared thin pool
- Volumes that are always exactly their physical size
- A way to compress data
- A read-only volume type
E Space is consumed from the pool only as data is written.
Q What is the main risk of thin provisioning?
+ Over-provisioning: if the pool fills, writes to any thin volume fail
- It is slower to read
- It cannot be snapshotted
- It uses more disk immediately
E Monitor the pool's Data% and Meta% and extend before it fills.
Q A striped logical volume (`--type striped -i 2`) improves:
+ Performance, by spreading I/O across multiple physical volumes
- Redundancy against disk failure
- Encryption
- Snapshot speed
E Striping has no redundancy; losing one PV loses the volume.
Q Which LVM RAID type gives mirroring (redundancy) across two devices?
+ raid1
- raid0
- striped
- linear
E raid1 keeps a full copy on each leg; it survives one device failing.
Q In `lvcreate --type raid5 -i 3`, what does -i specify?
+ The number of data stripes (RAID 5 also adds one parity's worth of space)
- The number of mirrors
- The extent size
- The snapshot size
E RAID 5 needs at least 3 devices and tolerates one failure.
Q Which command shows the underlying devices and segment type of LVs?
+ lvs -a -o +devices,segtype
- pvscan
- vgck
- lvchange -a
E It reveals which PVs each stripe/leg sits on.
C Create a 1 GiB thin pool named tpool in volume group vgdata.
A lvcreate --type thin-pool -L 1G -n tpool vgdata
A lvcreate -L 1G -T vgdata/tpool
E -T (or --type thin-pool) builds the pool that thin volumes draw from.
C Create a 5 GiB thin volume named tvol from the thin pool vgdata/tpool.
A lvcreate -V 5G -T vgdata/tpool -n tvol
A lvcreate --virtualsize 5G --thin vgdata/tpool -n tvol
E -V is the virtual size, which may exceed the pool's real size.
C Create a striped LV named fast across 2 PVs, 1 GiB total, 64 KiB stripe size.
A lvcreate --type striped -i 2 -I 64 -L 1G -n fast vgdata
E -i = number of stripes (PVs), -I = stripe size in KiB.
C Create a mirrored (raid1) LV named safe of 500 MiB in vgdata.
A lvcreate --type raid1 -m 1 -L 500M -n safe vgdata
E -m 1 means one mirror copy (two legs total).
T Thin provisioning end to end
S In vgdata create a 1 GiB thin pool, a 4 GiB thin volume, format and mount it, and watch pool usage grow as you write.
X lvcreate --type thin-pool -L 1G -n tpool vgdata
X lvcreate -V 4G -T vgdata/tpool -n tvol
X mkfs.xfs /dev/vgdata/tvol && mkdir -p /mnt/thin && mount /dev/vgdata/tvol /mnt/thin
X dd if=/dev/zero of=/mnt/thin/f1 bs=1M count=300
X lvs vgdata      # tpool Data% climbs toward 300 MiB used
V df -h /mnt/thin shows 4G; lvs shows the pool is only partly used
T Build and inspect a RAID1 volume
S Create a raid1 LV across two PVs, format and mount it, then show its legs and sync status.
X lvcreate --type raid1 -m 1 -L 500M -n safe vgdata
X lvs -a -o +devices,segtype,sync_percent vgdata
X mkfs.ext4 /dev/vgdata/safe && mkdir -p /mnt/safe && mount /dev/vgdata/safe /mnt/safe
V lvs -a shows two rimage/rmeta legs and 100% sync
T Extend a thin pool before it fills
S Simulate a nearly full thin pool and extend the pool (not just the volume) to avoid write failures.
X lvs vgdata      # note tpool Data%
X lvextend -L +1G vgdata/tpool
X lvs vgdata      # Data% drops as capacity grows
V the pool has more free space and thin volumes keep working
T Compare striped vs linear (concept + build)
S Create one linear and one striped LV of the same size and explain when you would choose each.
X lvcreate -L 500M -n lin vgdata
X lvcreate --type striped -i 2 -I 64 -L 500M -n strp vgdata
X lvs -a -o +segtype,devices vgdata
V # linear = simple/flexible; striped = faster I/O, no redundancy
